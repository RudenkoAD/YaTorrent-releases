# Эксперименты AIM2

Прочитай [подключение](../aim2-api/SKILL.md). Для нового списка запросов используй
[корзины](../aim2-api-baskets/SKILL.md), для выгрузки —
[результаты](../aim2-api-results/SKILL.md).

Различай определение experiment, конкретный запуск instance, варианты хостов
subexperiments и выходные SERPset. Одно определение можно запускать многократно.

## Подготовить определение

Нужны имя, basket_id и host_configs. Конфиг бери из запроса пользователя или
выбранного существующего определения (`GET /experiments/{id}`); не угадывай
host_type, CGI, регион или профиль исполнения. Списки:
`GET /experiments?limit=100&offset=0&q=<encoded-search>`.

```json
{
  "key": "<persisted-client-uuid>",
  "name": "Сравнение вариантов",
  "basket_id": 123,
  "host_configs": [
    {
      "host": {"host_type": "yandex.ru", "region": 213, "device": "DESKTOP", "search_type": "web", "cgi": {}},
      "meta": {"name": "Контроль", "batch_size": 50}
    }
  ]
}
```

Пример показывает структуру, а не рекомендуемый рабочий хост. Для второго
варианта добавь второй `{host,meta}` с согласованными отличиями. Весь host JSON
передаётся воркеру; meta — локальные подписи и размер батча. Не добавляй `items`
в корзинный формат. Поля query из корзины имеют приоритет: region_id → regionId
→ region; device/search_type также перекрывают значения хоста при наличии.

Сгенерируй UUID и сохрани его в payload до `POST /experiments`. После сетевого
сбоя повторяй тот же payload с тем же key. Смена payload с тем же key даёт
конфликт. Прочитай созданное определение по ID и проверь поля. У определения
нет обычного PUT: для другого конфига создай новое с новым key.

## Запустить

Если запуск входит в поручение, проверь выбранную корзину, runtime и объём:
число строк × число хостов. При старте нужны 1–100 хостов, не более 100000
запросов суммарно, batch_size 1–100 (по умолчанию 50). Сохранённый draft может
содержать неисполняемый конфиг: успешное создание ещё не валидирует воркер.

1. `GET /experiments-runtime`; при disabled сообщи ограничение, не меняй сервер.
   В mock выполняются синтетические задания; не выдавай их за реальные данные.
2. Сохрани отдельный новый UUID запуска в локальный JSON-файл:
   `{"request_id":"<persisted-launch-uuid>"}`.
3. `POST /experiments/{id}/instances` с этим файлом. При неизвестном исходе
   повтори тот же request_id, чтобы получить прежний instance. Новый UUID
   создаёт новый запуск; не используй его как средство починить таймаут клиента.
4. Прочитай `GET /experiment-instances/{instance_id}`. Ревизия корзины и конфиги
   фиксируются в момент запуска; последующие правки корзины его не меняют.

| Проверка | GET |
| --- | --- |
| История эксперимента | `/experiments/{id}/instances?limit=100&offset=0` |
| Прогресс хостов и выходы | `/experiment-instances/{id}` |
| Замороженный конфиг | `/experiment-instances/{id}/config` |
| Ошибки батчей | `/experiment-instances/{id}/batches?limit=100&offset=0` |
| Детали одного батча при диагностике | `/experiment-batches/{batch_id}` |

Опрос делай с ограничением по времени и разумным интервалом, например 10 секунд;
не создавай новый запуск, пока ждёшь старый. При выходе из сессии оставь ID и
последнее состояние. Не создавай фоновое расписание без запроса пользователя.

Новый сбор по хосту завершается failed, если любой батч упал, но успешные строки
сохраняются. Даже пустой SERPset может принадлежать failed-хосту. Проверяй
successful_items/failed_items и все subexperiments, а не только родительский статус.
postprocess_status и postprocess_error показывают отдельную стадию подклейки
оценок/метрик. Её ошибка не требует повторного сбора HTML. Если пользователь
поручил повторить именно обработку, используй
`POST /experiment-subexperiments/{id}/postprocess/retry` после проверки состояния;
не подменяй это новым instance.
